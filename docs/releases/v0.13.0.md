## v0.13.0 — Production pass

Two merged pull requests: dagre for the run-graph layout (#68) and a four-seat production
review — Staff, Product, Security, CTO — over surfaces earlier passes had not reached (#69).
Every accepted finding landed with a test that fails on the old code; every dismissed
candidate is recorded with its reason. The browser still derives no state.

### Fixed

- **Worker loop survives a transient store error.** `run_forever` exited on any exception
  escaping `_process` — a PostgreSQL blip stalled every run until someone restarted the
  process. The loop is now a logged, backed-off boundary (`error_backoff_seconds`, default
  1 s); `run_once` still raises so callers see the fault, and the periodic recovery sweep runs
  inside the boundary too. The boot sweep stays outside on purpose: a store that is down at
  start is loud. New FAIL_MODES row "Worker loop".
- **`GET /runs` folds only the page it returns.** It folded every run in the store to return
  fifty. It now walks `list_run_ids` newest-first (ordering by creation is stated on the port
  and held by all three stores) and stops at `limit`.
- **Request-body size limit.** `AGENTOS_MAX_BODY_BYTES` (default 1 MiB): 413 when
  `Content-Length` exceeds it, 411 for a chunked request with no length, both decided before
  the body is read; `GET`/`HEAD` and bodyless `POST`s pass. The self-review caught the first
  cut keying on a stray `Content-Type` header, which would have broken the README's own
  `curl -X POST .../cancel`.
- **Paged event reads.** `GET /runs/{id}/events` takes `limit` (1..5000, default 1000) and
  returns `has_more`; `read_events` grew an optional `limit` on the port and all three
  adapters (verified on live PostgreSQL). The UI fetches incrementally from `last_seq`
  instead of re-downloading the whole log on every stream frame, merges pages by `seq`
  (two overlapping refetches used to duplicate timeline rows), and bounds the walk.
- **Claims match the failure modes.** README and DESIGN said the engine "never double-runs
  a step"; FAIL_MODES row 41 says a step interrupted before its commit re-runs with exactly
  one completion recorded. The prose now says what the row says.
- **`ui/package.json` engines** said Node ≥ 18.18; CI runs 20 and one dependency wants 22.
  Now `>=20`, with the `EBADENGINE` warning documented.

### Graph layout

`@dagrejs/dagre` 3.1.1 (MIT) behind the existing `layout()` contract in `ui/src/graph.ts`.
Edges carry the router's waypoints and draw as smooth paths; a wide fan no longer crosses,
and a span-2 edge no longer cuts through the band it skips. Columns are pinned to the
scheduler's waves through per-edge `minlen`, because dagre's default ranker drew a source
with one long edge beside later nodes — which an operator reads as "starts later". Bundle
+15 KB gzipped; zero CSP violations in headless Chrome.

### Events and API

No new event types; golden logs unchanged. New query parameter `limit` and response field
`has_more` on `GET /runs/{id}/events`; new setting `AGENTOS_MAX_BODY_BYTES`; new worker
setting `error_backoff_seconds`. Both list endpoints keep their shapes.

### Numbers

527 Python tests collected (`tests` + providers, chaos included); UI tests 45 → 54;
FAIL_MODES at 68 rows. cqa held exactly (DSA 7.72 / Design 9.41 / Maturity 9.68).

### Declared bound, not fixed

`GET /approvals` and the recovery sweep still fold every non-terminal run to filter on
status. Removing that needs a denormalised `runs.status` column maintained on append — a
migration and a second copy of a fact the log already holds. Recorded in the ROADMAP with
what it would take; do it when a deployment has enough runs for the sweep to matter.
