## v0.15.0 — Operator UI shell, Node 22 toolchain, action majors

Five merged pull requests since `v0.14.0`: a professional shell for the operator UI (#91),
the Node 22 toolchain that lifts every held UI major in one lockfile (#85), the corrected
held-majors ledger (#84), and the ten GitHub Actions majors Dependabot proposed after
`v0.14.0`, consolidated into two verified changes (#83, #92). No engine, store, API or event
changes: golden logs are unchanged and no settings were added.

### Operator UI

The first light-mode screenshot from a real browser showed a flat page with no shell, a
banner that read as a paragraph, and a decision card whose actions looked secondary. The UI
now has:

- **A sticky top bar** — brand mark, auth-mode chip, Approvals / Runs tabs with a
  pending-count badge (mirrored into the tab title), and the identity on the right:
  `Acting as <id> · verified by the API` in bearer mode, or an amber *Unverified* bar with the
  principal input and a `why?` popover in asserted mode.
- **Page headers** with a one-line purpose on the inbox and runs pages; an empty inbox says
  what puts a run there.
- **Approval card** — workflow · run · kind · effect chips on one line, the decision in its own
  footer (reason input, primary Approve, danger Reject), and the "who is deciding" hint next to
  the disabled buttons.
- **Run page** — breadcrumb, `workflow <id>` header, and one card per section (Graph, Cost and
  latency, Timeline, Live frames), each with a header row stating what the section shows,
  including whether the graph is the live fold or the server's fold at a seq.
- **Sign-in and unreachable-API** states as centred cards; the run-log promise moves from the
  masthead tagline to the footer.

All state colours still come from the shared tokens; the browser derives nothing new. The
self-review over the shell commit caught the pending-count badge polling `GET /approvals`
every 5 s on every page on top of the inbox's own poll — doubling reads of the endpoint that
folds every non-terminal run — and going stale for a cycle after a decision. Now the inbox
reports its count upward while mounted and the shell polls at 15 s elsewhere; the test fails
on the previous shell (2 requests on first paint vs 1).

### Toolchain

Node 20 reached end-of-life on 2026-04-30 and was the real blocker behind every held UI
major (the ROADMAP had wrongly recorded "vitest 5 requires vite 8"; vitest 5's peer range
accepts vite 6.4 — what it requires is Node 22). #85 moves the three `ci.yml` steps and
`publish.yml` to Node 22 and takes vite 8.3.0, `@vitejs/plugin-react` 6.1.1, vitest 5.0.1,
jsdom 30.1.0 and TypeScript 7.0.2 together in one lockfile. TypeScript 7's new `TS2882`
check on the side-effect `import './styles.css'` is satisfied by adding `vite/client` to
`tsconfig` `types` rather than a hand-written ambient declaration. `npm audit` reports zero
vulnerabilities at every level; no majors are held.

### Actions

Ten Dependabot action bumps, all in workflows, consolidated into #83 (docker/login-action
4.6.0, metadata-action 6.2.0, setup-qemu-action 4.4.0, setup-buildx-action 4.4.1,
download-artifact 8.0.1) and #92 (checkout 7.0.1, setup-node 7.0.0, upload-artifact 7.0.1,
action-gh-release 3.0.3, build-push-action 7.4.0). `publish.yml` sits outside CI's path
filter, so those PRs carried no checks; the gate was re-resolving each new SHA against its
upstream tag's commit and a publish dry run from each branch, whose log shows the new pins
downloaded and executed. The common change across the majors is the action runtime moving
to Node 24. This tag is the first real run of `action-gh-release@v3` (the `release` job is
skipped by dry runs).
